This project coordinates a crowd-sourced effort to turn the announced Lean formalisation of four-dimensional Yang–Mills theory into a human-readable proof. The intended result is a research monograph giving detailed proofs of the argument, with statements and reasoning traceable to a fixed version of the formalisation. Existing mathematical results should be found and cited wherever applicable. Authors explain their application and prove any additional steps or variants; standard machinery implemented in Lean need not be reproved in the monograph.

Current stage: source imported; preliminary dependency mapping under way. The source is pinned to revision 3456e5e75cf8d4cd558955a5c7638fba2d68f464. The 17 audited release roots and a first-pass mathematical decomposition are recorded in the source audit, proof outline, and provisional unit plan. A full build, axiom audit, and line-by-line mathematical audit are still outstanding.

Contribute an agent

  1. Read CONTRIBUTING.md and AGENTS.md.

  2. Look at the issues and open pull requests. Choose one small, ready task and check for overlapping work.

  3. Post a scoped self-claim with a UTC expiry, recheck for conflicts, and begin. No manual approval is required.

  4. Work in your own fork or worktree. Submit one focused pull request with evidence.

Use the copy-and-paste agent prompts. The same workflow works with Fable, Codex, and other tools: explicitly give the agent AGENTS.md if its tool does not load that file automatically.

How the work fits together

Start at the final theorem and work backwards to a graph of mathematical results. Identify results that can be supplied by the literature, and agree on the statements and interfaces requiring exposition. Write detailed LaTeX proofs as soon as each local interface is precise; do not wait for the whole blueprint. Track outstanding prerequisite proofs explicitly. Prioritise shared definitions and results needed by many other parts. A proof unit can span several files; a large file can contain several units. Formal helper declarations do not each become a writing task. 

flowchart LR
    A[Pin and audit Lean source] --> B[Map theorem dependencies]
    B --> C[Find literature results and agree on proof units]
    C --> D[LaTeX sections and linked blueprint records]
    D --> B
    D --> E[Lean correspondence review]
    D --> F[Mathematical review]
    E --> G[Integrate the exposition]
    F --> G

GitHub issues are the live task queue and discussion space. Pull requests hold proposed changes and reviews. The repository holds the resulting knowledge; Bots/ preserves concise handoffs and discoveries, rather than a running chat log. See the coordination rules.

The Lean source, proof map, and English exposition have separate roles. Passing Lean checks does not establish that an English argument accurately describes the formal theorem; that correspondence requires review. See Lean's proof validation guidance.

Prior dependency mapping

The initial source clustering and much of the navigation data used by this repository come from Scott Armstrong's Yang-Mills informalization project. That project supplies the same-revision theorem restatement, 32-unit source map, declaration ownership table, selected statements, glossary, and work-item catalog. This repository's first-pass monograph outline adapts that work into proposed mathematical proof units; it does not claim the underlying mapping as original. See the pinned attribution and methodological limits.

Before opening the queue

Follow the maintainer launch checklist, including selecting licences and importing the source. The first tasks are source verification, statement auditing, dependency extraction, and one pilot explanation. Scale up after the pilot establishes a useful format and realistic task size.

Local structural checks require Python 3.9 or newer: 

python3 scripts/check_blueprint.py
python3 -m unittest discover -s tests

These checks validate metadata and review freshness. They do not compile Lean, verify English mathematics, or reserve tasks. No claim bot is installed; a contributors self-claim in issue comments and recheck for conflicts.
