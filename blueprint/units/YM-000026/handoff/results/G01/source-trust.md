What `VerifyJoint.lean` does, according to `source/evidence/axioms-3456e5e.md` and a reading of the script's control lines (`Lean/VerifyJoint.lean`, 107 lines, SHA-256 `f84e8b30…d3ec6`; lines 9–64 were read in the revision pass, lines 65–107 only through the search recorded in `validation.md`). (1) It imports `Challenge` into a separate environment, rejects any implementation module there, and checks that `YangMills.jointExistence` has the same type and universe parameters in the reference and in the solution (lines 21–30); this endpoint comparison is made for `jointExistence` only. (1a) While traversing the closure of the 17 roots, for every reached declaration owned by `PublicTheory`, `PublicWilson` or `ChallengeSpec` it requires the reference to contain a declaration of the same name with equal type, universe parameters and body (lines 55–59). This matters: equality of the endpoint type as an expression would not by itself show that the definitions it names agree. (1b) For every reached constant outside the project (the external boundary) it collects transitive axioms and rejects any non-standard one (lines 46–52); it also rejects unsafe or partial project declarations and project axioms (lines 60–61). (2) For each of the 17 roots it collects the transitive axioms and rejects anything outside `propext`, `Classical.choice`, `Quot.sound`. (3) It builds a base environment from the external modules only, checks that no project module and no endpoint is already in it, and calls Lean's `Environment.replay` on the 100,168 project declarations reachable from the 17 roots. The 14,364 "external" constants are the boundary: they are required to be present in the imported external environment and are not themselves replayed (I, from the script's `Missing pinned external dependency` check and the evidence text). The reference file `Lean/Challenge.lean` contains a deliberate `sorry` (line 5) as the proof of its copy of `jointExistence`; the verifier uses that declaration only for the type comparison, and the replayed proof is the one from `Solution.lean`, whose axiom report contains no `sorryAx`.

For `YangMills.jointExistence` in particular the evidence is therefore: its statement in the solution environment is syntactically the statement of `Lean/Challenge.lean` over the four frozen files listed in `Lean/verification/challenge.sha256` (`PublicTheory.lean`, `PublicWilson.lean`, `ChallengeSpec.lean`, `Challenge.lean`; G01 checked that the first four hashes in that file equal the current files, see `validation.md`); its proof term and everything it reaches inside the project were re-checked by the Lean 4.32.0 kernel, on macOS arm64, from object files compiled by a third party on Linux x86-64; and its axiom closure is the three standard axioms, with no `sorryAx`, no project axiom and no `Lean.ofReduceBool`.

## What this evidence does not cover

1. It is not a compilation from source. No `.lean` file of the project was elaborated on the audit host apart from the verifier scripts and the aggregate `YM` root. The kernel replay checks the declarations stored in the restored `.olean` files; that these are what the pinned sources elaborate to rests on Lake's trace comparison (`--no-build`), not on re-elaboration. This is the gap issue #37 addresses.
2. Trust in the pinned Lean binary and kernel (one implementation, one version), in `Environment.replay`, and in the external packages as delivered by the Mathlib cache: the pinned external repositories (nine according to `Lean/README.md`, Mathlib among them) were neither rebuilt nor replayed.
3. The standalone Comparator executable was not run, by upstream (`Lean/README.md`: "The standalone Comparator executable was not run") or by this project (`source/audit.md`). `Lean/comparator.json` is a configuration for it only.
4. `verification/CompactCheck.lean` and the upstream negative controls were not run by this project.
5. The 150,151 project declarations outside the closure of the 17 roots were not replayed.
6. Adequacy of the statement. Neither an axiom report nor a kernel replay says that `JointExistence` expresses the intended mathematics. That is the subject of `statement-ledger.md`; its Part C lists the points where the formal statement is weaker than a natural reading, and `adequacy.md` shows that the public statement alone does not force the selected theory to arise from the lattice measure.
7. The upstream README's sentences about the build ("The public reference was built with only the pinned external libraries on the search path. The solution build re-elaborated all new modules and reused compiled modules of the previously checked Wilson release.") describe upstream's own run; this project has no independent record of it.

## Source manifest

`source/build.md` states that `shasum -a 256 -c SOURCES.sha256` "had previously passed" with "All 9,507 listed files reported `OK`". Observation established under issue #37 and relayed to G01: in a fresh clone at `5535cc1`, `sha256sum -c SOURCES.sha256` reports 9,497 files OK and 10 absent, the absent ones being exactly the ten `verification/*.log` files listed in the manifest, which are not tracked in the Git import. The sentence in `source/build.md` is therefore not reproducible from the repository. No `.lean` file is affected. G01's own partial checks agree with this: `Lean/SOURCES.sha256` has 9,507 lines, ten of which name `verification/*.log`; `git ls-files Lean/verification` lists no `.log` file; and the thirteen public Lean files plus `YM/Nonperturbative/HeadlineSpec.lean` verify against the manifest (`validation.md`). A proposed correction is P8 in `proposed-patches.md`.

## Clean rebuild (#37): result

Inserted by the parent session from the #37 record, draft PR [#67](https://github.com/hairer/humanise-yang-mills/pull/67), file `source/evidence/clean-build-3456e5e.md` on that branch. That record is author evidence awaiting independent review; G01 did not repeat the build.

On 12 November 2026 every project module was compiled from source on an independent Linux x86-64 host (Fedora 44, official `leanprover/lean4:v4.32.0` binary, commit `8c9756b28d64dab099da31a4c09229a9e6a2ef35`), from an empty project build directory and without the prebuilt artifact, in a fresh clone of this repository at `5535cc1`. Results as recorded there:

- `lake build WilsonReference WilsonConstruction`: `Build completed successfully (18126 jobs).`, no failed job; `--no-build` recheck and `lake build YM` pass.
- `VerifyJoint.lean`: `TYPE_MATCH YangMills.jointExistence`; each of the 17 endpoints, among them `YangMills.jointExistence` and `YangMills.constructed`, reports `[propext, Classical.choice, Quot.sound]`; `REPLAY_PASS project=100168 external=14364 endpoints=17 duplicateAliases=0`.
- `CompactCheck.lean`, `Inventory.lean` (`declarations=249713 directSorryAx=0 projectAxioms=0`) and `Usage.lean` (`project=250319 used=100168 outside=150151`) pass. All counts equal those of the prebuilt-artifact audit under #2.

What this adds to the #2 evidence: the project's own `.lean` files have now been elaborated and kernel-checked from source on a second host and platform, and the kernel replay of the 100,168 reached declarations was repeated on those freshly compiled objects. What it does not add: Mathlib and the other pinned packages were taken from their caches on both hosts; the same Lean kernel implementation was used; the Comparator executable was not run; and neither audit bears on the adequacy of the statement (see `adequacy.md`).

Two observations from the #37 record qualify the #2 evidence. First, the manifest check in the Git import gives 9,497 files `OK` and 10 absent, as described above. Second, compared file by file with the prebuilt artifact used under #2, the fresh build's generated C files and `.ilean` files are all byte-identical, but 1,044 of the 9,470 `.olean` files differ, each being 8 or 16 bytes longer in the fresh build. **Update (12 November 2026, #37 follow-up, draft PR #75):** the cause is determined. Those modules store linter messages that carry the absolute path of the source file, and the two builds ran under root paths of different length; recompiled under a root path of the same length, all 1,044 modules equal the artifact's files after substituting the path. The prebuilt artifact is therefore, up to that embedded path, byte-for-byte the output of the pinned source, and the two bodies of kernel-replay evidence concern the same compiled content.

**Comparator (12 November 2026, draft PR #78, `source/evidence/comparator-3456e5e.md`).** The standalone Comparator executable, which upstream's README records as not run, was run sandboxed on a copy of the clean build for `YangMills.jointExistence`: `Lean default kernel accepts the solution`, `Your solution is okay!`, exit status 0. Qualifications recorded there: the shipped `comparator.json` needs the field `enable_nanoda` for Comparator `v4.32.0` (the run set it to `false`, so no external kernel was used); Comparator needed a one-line upstream fix to work with the current `landrun`; and Lake replayed the existing compiled objects, so nothing was recompiled inside the sandbox. A Comparator pass concerns the proof of the stated theorem, not the adequacy of the statement (`adequacy.md`).
