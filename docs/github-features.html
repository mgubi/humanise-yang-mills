Using GitHub Projects and Agents

Use one Project as a shared task dashboard. Keep GitHub-hosted agent sessions an optional way to execute tasks, alongside contributors' local tools. Issues remain the authoritative task records and claim discussion; PRs remain the review channel.

Projects

A GitHub Project presents linked issues and PRs as tables, boards, or roadmaps, with custom fields and saved views. It can belong to a user or organisation and be linked to this repository. See About Projects.

Start with a public project called Humanise Yang-Mills, if the repository is public, and use real task issues as its items. Convert any draft project card to an issue before claiming it. Display title, assignees, and labels; optionally add an Area field for mathematical subjects. Keep session IDs, exact claim expiries, scope, and evidence in the issue rather than duplicating them in custom fields.

Suggested saved table views:

View Filter
Ready is:issue is:open label:"status:ready"
Active is:issue is:open label:"status:claimed"
Needs review is:issue is:open label:"status:in-review"
Blocked is:issue is:open label:"status:blocked"
Literature is:issue label:"kind:literature"
Completed is:issue is:closed label:"status:done"

These views reuse the issue labels already defined in the coordination protocol. Project Status is a separate field, not an automatic copy of those labels. Hide it initially rather than maintaining a second independent task state. A later board can use Status once a reliable update/synchronisation policy is agreed. See project filters.

Configure the built-in auto-add workflow for this repository with is:issue. Add existing issues manually: enabling auto-add does not backfill them. This requires no custom claim bot. See auto-add.

Review the default workflows. GitHub can mark a project item Done when an issue closes or a PR merges. For this project, a merged draft is not completion of its mathematical task. Keep task issues open until their acceptance criteria are met; do not add an automation that treats draft merging or a card movement as approval. See built-in workflows.

Project access is separate from repository access. Give coordinators Project Write and retain the appropriate repository permissions for changing issue assignments and labels. Public contributors can read the dashboard without editing it. See project access.

Agents

The Agents interface launches and tracks supported coding-agent sessions. An enabled agent can start from a prompt or issue assignment and produce a PR or other artifact. Current partner integrations include Claude and Codex; availability depends on enabled policies and the subscription. Hosted partner sessions consume GitHub AI credits and Actions minutes. See coding agents.

Copilot sessions expose logs and controls for monitoring and stopping work. Some integrated local sessions can also be shared; this is tool-dependent. Keep the issue/PR workflow usable for every contributor, whether or not their tool's session appears in Agents. See session management.

Use hosted agents initially for bounded tooling, indexing, citation checking, or one pilot proof task. Evaluate the available model, source access, literature access, and Lean environment on that pilot before distributing mathematical work widely. The fact that a session completed does not establish that its proof is acceptable.

To launch a hosted task under the existing claim protocol:

  1. Select an unclaimed ready issue and identify the human responsible for the run.

  2. Post a self-claim with a unique session identifier, scope and UTC expiry; recheck for conflicting claims before assigning or launching the agent.

  3. Supply the issue URL, claim URL, identifier, budget, and repository instructions in the launch prompt. Record the resulting session URL on the issue.

  4. The responsible human monitors the session and ensures it stops or posts a valid renewal before expiry. The claim time is not a GitHub-enforced session timeout.

  5. Link the resulting PR or research artifact to the issue and apply the usual independent review requirements.

Do not dispatch the same writing task to several agents by default. Intentional independent reviews or comparisons must have explicit scope and separate outputs. Do not automatically launch an agent whenever a task becomes ready: that would compete with volunteers claiming tasks through the same queue.

This guide describes the intended setup. It does not create a live Project, enable agents, start sessions, or change billing settings.
